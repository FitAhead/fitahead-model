# FitAhead 캐릭터 설계

이 문서는 **왜 이렇게 만들었는지**를 기록합니다. 어떻게 쓰는지는 [README](../README.md)를 보세요.

---

## 1. 왜 Khronos RiggedFigure를 베이스로 쓰지 않았나

출발점은 [glTF-Sample-Models / RiggedFigure](https://github.com/KhronosGroup/glTF-Sample-Models/tree/main/2.0/RiggedFigure)
였습니다. 실제로 받아서 열어본 결과, 요구사항 4개 중 3개를 구조적으로 만족할 수 없었습니다.

| 요구사항 | RiggedFigure | 이유 |
|---|---|---|
| 얼굴에 사용자 그림 붙이기 | ❌ | 메시에 `TEXCOORD_0`(UV)가 **아예 없음**. 텍스처를 입힐 좌표가 없습니다. |
| 몸이 점점 커지는 표현 | ❌ | 모프 타겟 없음. |
| 남/여 구분 | ❌ | 단일 무성 프록시 메시 하나. |
| 얼굴 | ❌ | `neck_joint_2`에서 끝남 — 머리 지오메트리가 없습니다. |
| 부위별 확대 | △ | 조인트 19개는 참고할 만함. |

UV가 없다는 게 결정적이었습니다. 나중에 UV를 언랩하려면 결국 메시를 다시 만들어야 하고,
그럴 바에는 처음부터 우리가 제어하는 편이 낫습니다.

**대신 채택한 것**: RiggedFigure의 *조인트 토폴로지*(torso 체인 + 좌우 대칭 팔·다리 체인)를
참고하고, 메시 자체는 **파라메트릭 생성기**로 만듭니다. 얻는 것:

- 남/여를 같은 코드에서 파라미터만 바꿔 생성 → 두 프리셋이 절대 어긋나지 않음
- 모프 타겟을 마스크 함수로 정의 → 근육 그룹 추가가 함수 하나 추가
- 얼굴 플레이트의 UV를 우리가 원하는 대로 설계
- 에셋이 Git에서 **재현 가능**하고 diff 가능 (Blender 파일 블랙박스가 아님)

## 2. 몸 만드는 방법

### 2.1 지오메트리

몸통은 **로프트**(단면 링을 쌓아 올림), 팔다리는 **테이퍼드 튜브**, 머리·손은 **구**입니다.
전부 `tools/fitahead_gen/geom.py`.

몸통 단면은 `rx`(좌우) / `rz`(앞뒤)가 따로 있는 타원이라, 어깨는 넓고 허리는 좁고
골반은 다시 넓어지는 실루엣이 나옵니다. `torso_squash`로 타원을 살짝 사각형 쪽으로
밀 수 있지만 1.03 근처가 한계입니다 — 더 올리면 사람이 아니라 자판기처럼 보입니다.

**면 방향(winding)은 계산하지 않고 검사합니다.** 수직으로 쌓는 몸통 로프트와
임의 축을 따르는 팔다리 튜브는 기저(basis) 손대칭이 반대라, 한쪽을 맞추면 다른 쪽이
뒤집힙니다. 그래서 각 면을 만들 때 바깥 기준점과 법선을 비교해서 필요하면 뒤집습니다
(`add_quad_facing`). 손으로 유도한 winding은 실수해도 **렌더링 전까지 보이지 않기 때문에**
이쪽이 안전합니다.

### 2.2 관절 처리

팔꿈치·무릎은 **양쪽 튜브의 반지름을 정확히 일치**시켜 이음매를 없앴습니다.
어깨(삼각근)는 처음에 별도 구를 붙였다가 걷어냈습니다 — 구와 튜브가 만나는 자리에
주름이 생기는데, 하필 `shoulders` 모프가 부풀어 오르는 바로 그 위치였습니다.
지금은 위팔 튜브 자체의 둥근 캡(`round_start`)이 삼각근 역할을 합니다.

### 2.3 스키닝

정점마다 파트 태그가 있어서 (`upperarm_L`, `torso` …), 어떤 본에 붙일지 탐색할 필요가
없습니다. 사지는 주 본에 붙되 세그먼트 시작 32% 구간에서 부모 본으로 부드럽게 섞이고,
몸통은 높이에 따라 `Hips`/`Spine`/`Chest`로 블렌딩합니다.

가중치가 0인 조인트 슬롯은 인덱스를 0으로 강제합니다. glTF 스펙상 경고 대상이고,
일부 런타임은 4-influence 예산에 그대로 계산해 넣습니다.

## 3. 성장 표현 — 모프 타겟

### 3.1 왜 본 스케일이 아니라 모프인가

본을 굵게 스케일하면 관절이 늘어나 보이고, 가슴처럼 "앞으로만" 커져야 하는 부위를
표현할 수 없습니다. 모프 타겟은 정점을 **법선 방향으로** 밀기 때문에 부위별로
방향과 범위를 정확히 제어할 수 있습니다.

### 3.2 마스크 방식

각 그룹은 `(파트, 위치, 법선) → 0..1` 마스크 함수입니다 (`tools/fitahead_gen/morphs.py`).
예를 들어 `chest`는 "몸통 파트 + 가슴 높이 구간 + 앞을 향한 법선"이고,
`back`은 같은 높이지만 뒤와 옆을 향한 법선 — 그래서 등을 키우면 V자 실루엣이 나옵니다.

마스크가 위치 기반이라 **의상 셸에도 그대로 적용됩니다.** 반바지는 몸통·허벅지 파트로
태그되어 있어서, 엉덩이와 허벅지가 커지면 반바지도 같이 커집니다. 따로 처리하지 않습니다.

| 모프 | 부위 | 최대 변위(1.75m 기준) |
|---|---|---|
| `bulk` | 전체 체격 (머리 제외) | 2.2cm |
| `chest` | 가슴 | 4.3cm |
| `back` | 등 · 광배근 | 3.9cm |
| `shoulders` | 어깨 · 삼각근 | 3.6cm |
| `arms` | 팔 (이두 중심, 전완 약하게) | 3.2cm |
| `abs` | 복근 | 1.9cm |
| `glutes` | 엉덩이 | 3.5cm |
| `thighs` | 허벅지 | 3.2cm |
| `calves` | 종아리 | 2.9cm |
| `belly` | 뱃살 (역방향) | 7.5cm |

**인접한 마스크는 경계에서 0으로 만나야 합니다.** 위팔 마스크가 팔꿈치에서 0인데
전완 마스크가 0.39에서 시작하면, 팔꿈치를 빙 두르는 단차가 생깁니다. 실제로 처음에
그렇게 만들었고 렌더에서 바로 드러났습니다.

모프를 적용한 뒤 **법선을 다시 계산해서 그 차분도 함께 저장**합니다. 위치만 저장하면
몸이 커질 때 음영이 원래 형태를 따라가서 부풀어 오른 느낌이 죽습니다.

### 3.3 `belly`가 따로 있는 이유

"몸이 커진다"에는 두 방향이 있습니다. 근육이 붙는 것과 살이 찌는 것. 하나의 축으로
합치면 시작 상태를 표현할 수 없습니다. `belly`는 훈련량이 아니라 체성분에서 오고,
`isRegression: true`로 표시되어 있어 "성장" 집계에서 빠집니다.

## 4. 얼굴

머리는 구, 얼굴은 그 앞면에 얹힌 **구면 캡**(별도 메시 `Face`, 별도 머티리얼)입니다.
평면 원판으로 만들면 머리에 동전을 붙인 것처럼 보여서 구면을 따라가게 했습니다.

UV는 캡 전체가 0..1 정사각형에 **내접하는 원**으로 매핑됩니다. 즉 정사각형 이미지를
그대로 넣으면 원형으로 잘려 얼굴 위치에 똑바로 올라갑니다. 사용자 그림을 붙일 때
런타임에서 할 일은 `Face` 머티리얼의 base color 텍스처 교체 하나뿐입니다.

기본 얼굴은 눈 두 개와 입 하나 — 일부러 밋밋하게 만들었습니다. 사용자가 교체할
플레이스홀더라 개성이 있으면 오히려 방해가 됩니다.

## 5. 부위별 카메라

각 부위마다 타겟 지점 · 요/피치 각도 · 프레이밍 반지름이 매니페스트에 들어 있습니다.
거리는 앱이 런타임에 계산합니다. 두 가지 이유:

**세로 화면 보정.** 매니페스트의 거리는 정사각형 뷰포트 기준입니다. 폰은 세로라
수평 화각이 더 좁고, 세로 기준으로만 맞추면 팔 클로즈업에서 어깨가 잘려 나갑니다.
`FocusCamera`가 뷰포트 종횡비로 다시 계산합니다.

**구는 tan이 아니라 sin으로 맞춥니다.** 한계는 구가 만드는 시야각(절두체에 접함)이지
구 중심을 지나는 평면의 반폭이 아닙니다. tan을 쓰면 넓은 프레이밍에서 실루엣이 잘립니다
— `full_body`가 세로 화면에서 잘리는 걸로 테스트에서 잡혔습니다.

부위 프레이밍에는 **성장 여유분**이 들어 있습니다. 프레이밍은 기본 자세에서 계산되지만
사용자는 모든 성장 단계에서 그 화면을 보기 때문에, 최대치까지 부풀어도 넘치지 않도록
해당 그룹 + `bulk`의 최대 변위만큼 반지름을 키웁니다.

## 6. 성장 모델 (`GrowthModel`)

훈련량 → 모프 가중치 매핑은 **포화 곡선**입니다:

```
weight = maxWeight × (1 − 2^(−volume / halfVolume))
```

선형이 아닌 이유 두 가지. 실제 근비대가 그렇게 동작하고, 초반 변화가 크게 나와서
초보자가 **한 달이 아니라 몇 번의 세션 만에** 캐릭터가 변하는 걸 봅니다.

**디트레이닝**도 들어 있습니다. 쉬면 유효 훈련량이 감소하되, `retainedFloor`(기본 55%)
아래로는 내려가지 않습니다 — 머슬 메모리입니다. 이 바닥이 없으면 2주 휴가가 몇 달치
성과를 눈에 띄게 되돌리는데, 생리학적으로 틀렸을 뿐 아니라 동기부여의 정반대입니다.

`bulk`는 직접 훈련되지 않고 다른 그룹 평균의 85%를 따라갑니다. 한 부위를 훈련하면
그 부위가 커져야지 몸 전체가 부풀면 안 되기 때문입니다.

## 7. 매니페스트가 계약인 이유

`character_manifest.json`에는 조인트 목록(인덱스 포함), 모프 목록(인덱스·한/영 라벨·
최대 변위), 카메라 프레이밍, 얼굴 슬롯 정보가 들어 있습니다. GLB와 **같은 스크립트가
같은 실행에서** 생성하므로 어긋날 수 없습니다.

`packages/fitahead_character`의 테스트는 픽스처가 아니라 **실제 생성된 매니페스트**를
읽습니다. 생성기를 고쳐서 계약이 깨지면 Dart 테스트가 실패합니다.

## 8. 렌더러 선택 (미정)

이 레포는 의도적으로 렌더링 엔진에 의존하지 않습니다. 필요한 기능은 3개입니다:

1. 런타임 **모프 타겟 가중치** 제어 (성장)
2. 자유로운 **카메라 배치** (부위 확대)
3. 런타임 **텍스처 교체** (사용자 얼굴)

| 후보 | 방식 | 비고 |
|---|---|---|
| `three_js` | Dart 포팅, 네이티브 GL | three.js API 전체 — 세 기능 모두 직접 제어 가능. 성숙도 확인 필요 |
| `flutter_scene` | Impeller 네이티브 | Flutter 팀 계열. 자체 `.model` 포맷 변환 필요, 모프 타겟 지원 여부 확인 필요 |
| `model_viewer_plus` | WebView + `<model-viewer>` | 카메라 제어는 쉬움. 모프 가중치가 공개 API에 없음 |
| Unity / Godot 임베딩 | 별도 엔진 | 가장 강력하지만 앱 크기와 빌드 복잡도 급증 |

**추천은 `three_js`입니다** — 세 요구사항을 모두 직접 만족하는 유일한 순수 Flutter
후보이기 때문입니다. 다만 이 세션에서는 실기기 검증을 하지 못했으므로,
**작은 스파이크로 먼저 확인**한 뒤 확정하는 걸 권합니다: `male.glb`를 띄우고,
`chest` 모프 가중치를 슬라이더로 움직이고, 얼굴 텍스처를 하나 갈아끼워 보는 정도면
충분합니다.

렌더러가 정해지면 `packages/fitahead_character_<engine>`으로 얇은 위젯 패키지를 추가하고,
도메인 패키지는 그대로 둡니다.

## 9. 검증 방법

- **glTF 스펙**: Khronos `gltf-validator` 통과 — 두 프리셋 모두 에러 0 / 경고 0
- **시각 확인**: 헤드리스 Chromium + three.js로 렌더 (`docs/renders/`)
- **계약**: Dart 테스트 54개 (`packages/fitahead_character/test/`)
